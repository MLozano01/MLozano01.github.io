Software Developer, Search team — working on shipping estimation inside product search.
What the team owns
When someone searches for a product on Mercado Libre, every result needs a shipping estimate attached to it — cost, timing, availability — computed per listing, per search, for every seller and every client on the platform. My team builds and runs the systems that produce that estimate.
Why it's an interesting engineering problem
  • The computation sits directly in the critical path of search — it can't be async or best-effort, it has to return correct and fast, on every single search request across the platform
  • It runs at the scale of one of Latin America's largest e-commerce marketplaces, across many countries, sellers, and shipping configurations simultaneously
  • Any regression here doesn't fail quietly — it's visible on essentially every search, which makes reliability and latency budgets first-class engineering constraints, not afterthoughts
What I do day to day
Contribute to backend services and internal platform work for this pipeline, collaborating cross-functionally with the wider Search org in an agile workflow — balancing correctness, latency, and reliability on a system where "it usually works" isn't good enough.

type Desconectapp struct // capstone thesis, UBA — 2025
"A platform that matches strangers into small groups by shared activity, location, and free time — to get people offline and meeting face to face."
4
person team
1yr
development
O(N log N)

Problem
Most social apps optimize for time spent on-screen. We built the opposite: a system whose entire job is to get itself out of the way and put small groups of compatible strangers in the same physical place, at a time and place that works for all of them.
Designing the matching algorithm
The core design question: how do you group N pending requests into compatible clusters (same activity, overlapping availability, overlapping location radius, compatible group size) without the computation blowing up as usage grows?
  • Shipped: a dynamic-programming approach using an intermediate "partial match" structure that incrementally merges compatible requests, tested against every edge case the team could construct, with no found counterexample
  • Measured complexity: O(N log N) worst case, dominated by sorting partial matches by member count before a linear compatibility scan
  • Rejected: modeling requests as a graph and searching for cliques — finding a clique of a given size is NP-complete, and the target clique size wasn't even known in advance
  • Rejected: embedding-based similarity matching — added complexity without benefit, since compatibility here is categorical (same activity or not), not a fuzzy semantic match
Architecture
Deliberately monolithic, not microservices — a layered Handler → Service → Repository backend in Go/Gin, with sqlc generating type-checked Go from raw SQL instead of an ORM. A React Native + Expo mobile client shares one codebase across Android and iOS. Real-time group chat runs on Supabase (Postgres + Row-Level Security), bridged to the app's own JWT auth via a single token-issuing endpoint — avoiding a second, unsynchronized user table.
A production bug: database concurrency
Early versions used a single pgx.Conn to Postgres. Under concurrent requests from the frontend, this serialized every query behind the scenes — and certain delete operations left the connection in an invalid state, crashing the process outright. Migrated to pgxpool for proper connection pooling, eliminating both the serialization bottleneck and the crash.

class DistributedMovieAnalysisSystem
"A fault-tolerant, horizontally-scaled pipeline for analyzing large movie datasets across many concurrent clients."

Problem
Analyzing a large movie dataset (genres, ratings, credits, revenue) for multiple concurrent clients means the work can't run as a single script — it needs to be split, scaled, and kept correct even when individual pieces fail mid-run.
Architecture
Built as a pipeline of specialized, independently scalable node types connected through RabbitMQ:
  • filter — narrows records by criteria (decade, country, language), running multiple replicas in parallel
  • joiner — merges ratings and credits data streams into enriched records
  • aggregator / reducer — compute running metrics (top-5/top-10 lists, averages, budget sums) and checkpoint state to disk
  • data-controller — coordinates ingestion per dataset (movies, ratings, credits) across replicas
  • healthchecker — 3 replicated instances in the base configuration, each watching a distinct, partitioned subset of nodes so no single monitor is a point of failure; replica count is configurable and scales up as the node count grows
Proving it holds up
Wrote a custom chaos-engineering script that kills running node containers — either one at random every few seconds, or all of them at once — to force failure conditions on demand. Used it to validate that checkpointed reducer state and automatic node recovery meant no data was lost, regardless of which node went down or when.

struct DistributedOrderSystem // Concurrent Programming, FIUBA
"A fault-tolerant, actor-based system coordinating order-taking and fulfillment nodes over a custom TCP protocol, with no single point of failure."
2
cooperating node types
2
independent ring topologies
1
leader election algorithm
2
delivery rounds, reworked fault-tolerance design
Problem
Coordinate two distinct fleets of nodes — order-taking terminals and fulfillment units serving a shared, limited inventory — so that any single node (including the leader) can fail mid-order without losing or duplicating work, and without a central coordinator as a single point of failure.
Architecture
Built in Rust with an actor-based design across two node types:
  • Screens — take and pay for orders, form their own ring, and back each other up peer-to-peer (A backs up to B, B to C, C to A), so a failed screen's pending and completed orders are always recoverable from exactly one neighbor
  • Robots — arranged in a separate ring, fulfill orders, and elect a leader among themselves that bridges the two rings, distributing work and reporting completion back to Screens
  • All inter-node communication runs over raw TCP with a custom, hand-rolled protocol: enum-based message types, JSON serialization, newline-delimited framing
Distributed mutual exclusion over shared inventory
Each inventory item circulates the Robot ring as a token; a robot can only consume that item while holding its token, and passes it along when idle or already serving something else. If a token goes missing (e.g. lost during a robot failure), the discovering robot triggers a recovery pass: every robot reports the last quantity it saw, and the token is reissued with the lowest reported value — the most conservative, safest reconstruction available.
Reworking fault tolerance between deliverables
The first version detected robot failures with periodic heartbeat messages. After the first delivery, this was replaced with detection via the TCP connection itself — using the socket's own disconnect signal instead of polling — for faster, event-driven failure detection. Backup scope was also widened from two adjacent robots to all robots, trading a bit of redundancy for meaningfully higher resilience.
