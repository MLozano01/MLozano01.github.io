type Desconectapp struct // capstone thesis, UBA — 2025
"A platform that matches strangers into small groups by shared activity, location, and free time — to get people offline and meeting face to face."
4
person team
1yr
development
O(N log N)
matching algorithm
2
approaches rejected first
Problem
Most social apps optimize for time spent on-screen. We built the opposite: a system whose entire job is to get itself out of the way and put small groups of compatible strangers in the same physical place, at a time and place that works for all of them.
Designing the matching algorithm
The core design question: how do you group N pending requests into compatible clusters (same activity, overlapping availability, overlapping location radius, compatible group size) without the computation blowing up as usage grows?
  • Rejected: modeling requests as a graph and searching for cliques — finding a clique of a given size is NP-complete, and the target clique size wasn't even known in advance
  • Rejected: embedding-based similarity matching — added complexity without benefit, since compatibility here is categorical (same activity or not), not a fuzzy semantic match
  • Shipped: a dynamic-programming approach using an intermediate "partial match" structure that incrementally merges compatible requests, tested against every edge case the team could construct, with no found counterexample
  • Measured complexity: O(N log N) worst case, dominated by sorting partial matches by member count before a linear compatibility scan
Architecture
Deliberately monolithic, not microservices — a layered Handler → Service → Repository backend in Go/Gin, with sqlc generating type-checked Go from raw SQL instead of an ORM. A React Native + Expo mobile client shares one codebase across Android and iOS. Real-time group chat runs on Supabase (Postgres + Row-Level Security), bridged to the app's own JWT auth via a single token-issuing endpoint — avoiding a second, unsynchronized user table.
A production bug: database concurrency
Early versions used a single pgx.Conn to Postgres. Under concurrent requests from the frontend, this serialized every query behind the scenes — and certain delete operations left the connection in an invalid state, crashing the process outright. Migrated to pgxpool for proper connection pooling, eliminating both the serialization bottleneck and the crash.

class DistributedMovieAnalysisSystem
"A fault-tolerant, horizontally-scaled pipeline for analyzing large movie datasets across many concurrent clients."

containerized nodes
7

3

0

Problem
Analyzing a large movie dataset (genres, ratings, credits, revenue) for multiple concurrent clients means the work can't run as a single script — it needs to be split, scaled, and kept correct even when individual pieces fail mid-run.
Architecture
Built as a pipeline of specialized, independently scalable node types connected through RabbitMQ:
  • filter — narrows records by criteria (decade, country, language), running multiple replicas in parallel
  • joiner — merges ratings and credits data streams into enriched records
  • aggregator / reducer — compute running metrics (top-5/top-10 lists, averages, budget sums) and checkpoint state to disk
  • data-controller — coordinates ingestion per dataset (movies, ratings, credits) across replicas
  • healthchecker — 3 replicated instances, each watching a distinct, partitioned subset of nodes, so no single monitor is a point of failure
Proving it holds up
Wrote a custom chaos-engineering script that kills running node containers — either one at random every few seconds, or all of them at once — to force failure conditions on demand. Used it to validate that checkpointed reducer state and automatic node recovery meant no data was lost, regardless of which node went down or when.
Stack
Python · RabbitMQ · Docker & Docker Compose · custom chaos-testing tooling

Problem
A social feed needs to serve posts, handle engagement (likes, retweets, bookmarks), and support keyword search — as one deployable, testable piece of a larger, service-oriented product, not a monolith.
What I built
  • Feed generation, likes, bookmarks, retweets, topics, and keyword-based search, built in Go against MongoDB

  • A GitHub Actions CI pipeline running the test suite on every push, with coverage tracked via Coveralls
